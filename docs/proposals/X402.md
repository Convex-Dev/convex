# x402 payments — implementation notes

- Status: Implemented (initial version on develop)
- Specification: **[CAD042](https://docs.convex.world/docs/cad/x402)** is the
  normative spec — network and asset identifiers, the `exact` scheme binding,
  verification/settlement rules and facilitator behaviour all live there.
  This document covers only how this repository implements it.
- Upstream protocol: [x402 v2](https://github.com/coinbase/x402/blob/main/specs/x402-specification-v2.md)
- Last updated: 2026-07-31

## Summary

Convex supports the x402 payment protocol: HTTP-native payments using the
`402 Payment Required` status code, settled as ordinary Convex transactions
(CVM coin or CAD29 fungible tokens) with sub-second finality. A payment is a
pre-signed transaction constructed by the payer; a peer's REST server acts as
its own facilitator, so nothing in the flow signs on behalf of anyone or holds
funds. See CAD042 for the protocol binding and its rationale.

## Module: `convex-x402`

Transport-agnostic library (Java 21, depends only on `convex-core` and
`convex-peer`, no third-party dependencies):

| Package | Contents |
|---------|----------|
| `convex.x402` | `X402` (version, header names, base64 header codecs), `Fields` (JSON field names), `ErrorReasons`, `NetworkId` (CAIP-2 identity: genesis-hash form + `CAIP` aliases) |
| `convex.x402.model` | `PaymentRequired`, `ResourceInfo`, `PaymentRequirements`, `PaymentPayload`, `VerifyResponse`, `SettlementResponse` — records with `toJSON`/`fromJSON` over CVM maps |
| `convex.x402.scheme` | `ExactConvexScheme`: bounded storeless decode, structural check, state check |
| `convex.x402.facilitator` | `Facilitator` interface plus `ConvexFacilitator` (verify/settle against any `convex.api.Convex` connection, idempotent settlement) and `RemoteFacilitator` (HTTP client for any spec-compliant external facilitator, enabling foreign kinds such as USDC on Base) |
| `convex.x402.client` | `X402Client`: wraps `java.net.http.HttpClient`, pays 402 demands with locally-signed transactions |

## Key API surface

Signatures and semantics of the public API, for review and for agents working
against it. Javadoc on the classes is the authority for detail.

### Protocol core (`convex.x402`)

```java
public class X402 {
    static final int VERSION = 2;                       // x402Version implemented
    static final String HEADER_PAYMENT_REQUIRED;        // "PAYMENT-REQUIRED" (402 response)
    static final String HEADER_PAYMENT_SIGNATURE;       // "PAYMENT-SIGNATURE" (paid request)
    static final String HEADER_PAYMENT_RESPONSE;        // "PAYMENT-RESPONSE" (receipt)
    static final String SCHEME_EXACT = "exact";
    static final long MAX_HEADER_BYTES = 16384;         // decode bound, attacker-controlled input

    static String encodeHeader(ACell json);             // JSON -> base64 header value
    static AMap<AString,ACell> decodeHeader(String v);  // bounded; IllegalArgumentException on bad input
}

public final class NetworkId {                          // CAIP-2 identity of one network
    static NetworkId create(Hash genesisHash);
    String canonical();                                 // "convex:<32-hex genesis prefix>"
    boolean matches(String caip2);                      // canonical form or a CAIP alias
    List<String> knownForms();                          // canonical first, then aliases
}
```

`Fields` holds the exact JSON field names; `ErrorReasons` the x402 error
strings including the `invalid_exact_convex_payload_*` reasons.

### Model (`convex.x402.model`)

Records mirroring the x402 v2 schemas. Each has `AMap<AString,ACell> toJSON()`
and a static `fromJSON(AMap)` that throws `IllegalArgumentException` on
missing required fields.

```java
record ResourceInfo(String url, String description, String mimeType)
record PaymentRequirements(String scheme, String network, String amount,  // atomic units, base-10
        String asset, String payTo, long maxTimeoutSeconds, AMap<AString,ACell> extra)
record PaymentRequired(int x402Version, String error, ResourceInfo resource,
        List<PaymentRequirements> accepts)
record PaymentPayload(int x402Version, ResourceInfo resource,
        PaymentRequirements accepted, AMap<AString,ACell> payload)       // payload: {"transaction": <hex>}
record VerifyResponse(boolean isValid, String invalidReason, String payer)
record SettlementResponse(boolean success, String errorReason, String payer,
        String transaction, String network, String amount)               // transaction: "0x" + tx hash
```

### Scheme verification (`convex.x402.scheme.ExactConvexScheme`)

Stateless static methods; a `null` return from a check means "pass", a
non-null return is the x402 error reason.

```java
static final Symbol DIRECT_TRANSFER;                    // CAD29 transfer callable
static final long MAX_TRANSACTION_BYTES = 4096;         // decode bound
static final long FEE_ALLOWANCE = 1_000_000;            // copper headroom for juice fees

// Bounded, storeless decode; IllegalArgumentException on anything malformed
static SignedData<ATransaction> decodeTransaction(AMap<AString,ACell> schemePayload);

// The canonical transaction for these requirements, or null if unusable
static ATransaction expectedTransaction(Address origin, long sequence,
        Address payTo, PaymentRequirements req);

// Structural check: cell equality against the canonical transaction
static String checkStructure(SignedData<ATransaction> sd, PaymentRequirements req);

// State check via any client: signature vs current account key, next sequence, funds
static String checkState(Convex convex, SignedData<ATransaction> sd,
        PaymentRequirements req) throws InterruptedException;
```

### Facilitators (`convex.x402.facilitator`)

```java
interface Facilitator {                                 // the x402 facilitator role
    VerifyResponse verify(PaymentPayload payload, PaymentRequirements requirements);
    SettlementResponse settle(PaymentPayload payload, PaymentRequirements requirements);
        // failures are reported in the responses, never thrown
    boolean handles(String scheme, String network);     // routing; fails closed
    AMap<AString,ACell> supported();                    // /supported response body
}

class ConvexFacilitator implements Facilitator {        // settles on Convex directly
    ConvexFacilitator(Convex convex, NetworkId networkId);
    ConvexFacilitator(Convex convex, NetworkId networkId, Predicate<Hash> confirmedCheck);
        // confirmedCheck enables idempotent settlement of retried payments
        // settle: verify + submit + await Result, capped at MAX_SETTLE_TIMEOUT_MILLIS (30s)
    NetworkId getNetworkId();
}

class RemoteFacilitator implements Facilitator {        // any external facilitator over HTTP
    static RemoteFacilitator create(HttpClient http, URI baseUrl);
        // e.g. https://x402.org/facilitator — speaks the standard /verify /settle /supported API
    RemoteFacilitator withDecorator(UnaryOperator<HttpRequest.Builder> d);  // auth headers etc.
    RemoteFacilitator withKind(String scheme, String network);
        // explicit kinds; without any, kinds are discovered from /supported (cached, fail-closed)
}
```

The Convex-side service never verifies foreign chains itself: a
`RemoteFacilitator` delegates that (and settlement) to the external
facilitator, which is trusted to report honestly — the standard x402 posture.

### Paying client (`convex.x402.client.X402Client`)

static X402Client create(HttpClient http, Convex convex, AKeyPair keyPair);

### Gate and policies (`convex.restapi.handler`)

```java
record X402Decision(...) {                              // one request's fate
    static X402Decision allow();                        // serve free (e.g. credit consumed)
    static X402Decision charge(PaymentRequirements req);
    static X402Decision charge(PaymentRequirements req, String description);
    static X402Decision charge(List<PaymentRequirements> options, String description);
        // several acceptable options, e.g. CVM on Convex OR USDC on Base
    static X402Decision deny(int status, String message);
}

interface X402Policy {
    X402Decision decide(Context ctx) throws InterruptedException;
        // runs before payment processing; MUST be deterministic between 402 and retry
    default boolean onSettled(Context ctx, PaymentPayload payment, SettlementResponse receipt);
        // after settlement, before the handler; may fire again for the same tx on
        // retries — dedupe by receipt.transaction(); return false to refuse (402)
}

class X402Gate {
    X402Gate(Facilitator... facilitators);              // routing priority order
        // an incoming payment settles via the first facilitator whose handles()
        // accepts its (scheme, network); the client's accepted echo selects, but
        // never defines, the requirements — the server's own copy is settled
    void protect(RoutesConfig routes, String path, X402Policy policy);  // embedder entry point
    PaymentRequirements price(String amount, String asset, String payTo);
        // requirements against this gate's Convex facilitator network
    static X402Policy fixedPrice(PaymentRequirements req, String description);
    void installFromConfig(RoutesConfig routes, RESTConfig config);     // rest.x402.routes
    static String getPayer(Context ctx);                // payer for paid requests, else null
    static SettlementResponse getReceipt(Context ctx);  // receipt for paid requests, else null
}
```

### REST endpoints and config (`convex-restapi`)

`X402API` serves `POST /x402/verify`, `POST /x402/settle` (concurrency
limited) and `GET /x402/supported`; it is constructed by `RESTServer` only
when x402 is enabled and exposes `getFacilitator()`. `RESTConfig` accessors:
`isX402Enabled()` (default false), `isX402FacilitatorEnabled()` (default true
when enabled), `getX402PayTo()`, `getX402Routes()`.

## Implementation notes

Notes worth knowing:

- **Structural verification is cell equality**: `ExactConvexScheme` rebuilds
  the canonical transaction (`Transfer`, or the `direct-transfer` `Call`) from
  the requirements plus the presented origin/sequence, and requires the
  presented transaction to equal it. Every field is whitelisted at once; only
  origin and sequence remain free, and those are checked against state.
- **Decoding mirrors `PreparedTransaction`**: storeless
  (`Message.create(blob).getPayload(null)`), capped at 4 KiB
  (`MAX_TRANSACTION_BYTES`), so adversarial payloads never touch the peer
  store.
- **Fee allowance** is a deliberately generous fixed constant
  (`FEE_ALLOWANCE` = 1,000,000 copper): verification is advisory, settlement
  is the source of truth.
- **Idempotent settlement**: the facilitator takes an optional
  `Predicate<Hash>`; the REST wiring supplies
  `hash -> server.getPeer().getTransaction(hash) != null`, so a retried
  request whose payment already settled is served without a second charge.
- **Sequence reads bypass the client cache**: `X402Client.buildPayment` uses
  `Convex.lookupSequence`, not `getSequence` — the connection's cached
  sequence goes stale when payments settle out-of-band, and a reused sequence
  replays the previous payment instead of paying.

## REST API integration (`convex-restapi`)

- `convex.restapi.api.X402API` serves the facilitator endpoints
  (`POST /x402/verify`, `POST /x402/settle` under a `ConcurrentLimit`,
  `GET /x402/supported`) with OpenAPI annotations. Constructed only when
  x402 is enabled; the facilitator settles through the server's shared
  `ConvexLocal` and identifies the network from
  `server.getPeer().getNetworkID()`.
- `convex.restapi.handler.X402Gate` payment-gates configured paths as a
  Javalin before-handler: no `PAYMENT-SIGNATURE` → 402 with the
  `PAYMENT-REQUIRED` header (mirrored in the body) and
  `ctx.skipRemainingHandlers()`; a valid payment is settled
  (settle-before-serve) and the receipt set in `PAYMENT-RESPONSE` before the
  request falls through to the protected handler. A structurally unparseable
  payment header gets 400 (the transport's "invalid payment" mapping);
  payment failures on well-formed payments stay 402. Route configuration is
  validated fail-fast at startup.
- `RESTServer`'s CORS rules expose `PAYMENT-REQUIRED` and `PAYMENT-RESPONSE`
  so browser-based x402 clients can read them; embedders running their own
  Javalin apps must do the same for browser payers.
- Configuration (`RESTConfig`, JSON5), off by default:

  ```json5
  rest: {
    x402: {
      enabled: true,
      facilitator: true,        // /x402/* endpoints (default true when enabled)
      payTo: "#13",             // default recipient for gated routes
      routes: [
        { path: "/api/v1/premium/*",
          amount: "1000000",     // atomic units; string or integer
          asset: "slip44:864",   // default; or "cad29:<addr>"
          description: "Premium data access" }
      ]
    }
  }
  ```

## Embedding: custom payment policies

Services embedding Convex (e.g. Covia venues) can protect routes on their own
Javalin apps with custom payment logic. The gate is driven by an
`X402Policy` — per request it returns an `X402Decision`: `allow()` (serve
free), `charge(requirements[, description])`, or `deny(status, message)` —
and receives an `onSettled` callback when a payment lands, before the
protected handler runs. `X402Gate.fixedPrice(requirements, description)` is
the trivial policy the config path uses; credit semantics look like:

```java
Facilitator facilitator = new Facilitator(convex,
        NetworkId.create(server.getPeer().getNetworkID()),
        hash -> server.getPeer().getTransaction(hash) != null);
X402Gate gate = new X402Gate(facilitator);
gate.protect(routes, "/paid/*", new X402Policy() {
    public X402Decision decide(Context ctx) {
        if (creditsFor(caller(ctx)) > 0) { consumeCredit(caller(ctx)); return X402Decision.allow(); }
        return X402Decision.charge(gate.price("3000000", X402Client.cvmAsset(), "#13"),
                "Top up 3 calls");
    }
    public boolean onSettled(Context ctx, PaymentPayload payment, SettlementResponse receipt) {
        if (!recordOnce(receipt.transaction())) return false; // replay: already consumed
        addCredits(receipt.payer(), 2);                        // 3 bought, this call is one
        return true;
    }
});
```

To also accept foreign payment kinds — e.g. USDC on Base via a hosted
facilitator — combine facilitators and offer several options:

```java
Facilitator base = RemoteFacilitator
        .create(httpClient, URI.create("https://x402.org/facilitator"))
        .withKind("exact", "eip155:8453");
X402Gate gate = new X402Gate(convexFacilitator, base);
// in a policy:
return X402Decision.charge(List.of(
        gate.price("1000000", X402Client.cvmAsset(), "#13"),
        new PaymentRequirements("exact", "eip155:8453", "10000",
                "erc20:0x8335…2913", "0xServiceWallet", 30, null)),
        "Pay in CVM or USDC");
```

The gate routes the client's chosen option to the facilitator that handles
it; the Convex facilitator disclaims foreign kinds, and the remote
facilitator owns all foreign-chain verification and settlement. Hosted
facilitators needing API keys are configured via `withDecorator`.

The contract embedders must respect (spelled out in the `X402Policy`
javadoc):

- `decide` MUST be deterministic between the 402 and the paid retry, or the
  payment fails the amount check and the client sees a fresh 402.
- Settlement is idempotent, so `onSettled` can fire more than once for the
  same transaction; ledgers MUST dedupe by `receipt.transaction()` and SHOULD
  return false for a consumed replay (the gate then responds 402 instead of
  serving).
- An `onSettled` exception fails the request but the payment stays settled;
  a client retry settles idempotently and re-runs the hook, so deduplicating
  implementations converge.
- Downstream handlers read the payment via `X402Gate.getPayer(ctx)` /
  `getReceipt(ctx)`; on the free path, identity comes from the request's own
  authentication.

## Client usage

```java
Convex convex = ConvexHTTP.connect(peerUri, address, keyPair);
X402Client client = X402Client.create(httpClient, convex, keyPair);
HttpResponse<String> response = client.get(URI.create(paidUrl));
SettlementResponse receipt = client.lastPaymentResponse();
```

The client selects the first `exact`/`convex:*` requirement it can satisfy,
signs the canonical transaction locally, retries with `PAYMENT-SIGNATURE`,
and surfaces the decoded receipt. Payment construction is synchronised per
instance because payments consume sequence numbers.

## Testing

- `convex-x402` unit tests: model/header round-trips, adversarial decode
  bounds, canonical-form acceptance and every non-canonical shape rejection,
  network matching.
- `convex-restapi` `X402Test`: end-to-end against a real peer — payment
  demand, paid flow with balance movement, idempotent replay without
  double-charge, wrong-sequence rejection, facilitator verify/settle over
  HTTP, and a deploy-token-then-pay CAD29 flow. No sleeps, no fixed ports.
- `convex-restapi` `X402PolicyTest`: the embedder story — a standalone
  Javalin app (no `RESTServer`) gated by a credit policy: pay once for three
  calls, free calls while credit lasts, fresh 402 on exhaustion, and a
  consumed replay refused via the `onSettled` veto.
- `convex-restapi` `X402MultiSchemeTest`: foreign payment kinds — a gate
  offering CVM-on-Convex and USDC-on-Base, with the Base option settled
  through a stub external facilitator: both options offered, foreign payment
  routed and receipted, Convex payment unaffected, kind discovery from
  `/supported` failing closed, the Convex facilitator disclaiming and cleanly
  rejecting foreign kinds, and a tampered `accepted` echo refused before any
  facilitator is consulted.
- `convex-core` `TransactionTest.testCall` executes a wire-decoded `Call`
  (regression for the null-args bug this work uncovered).
