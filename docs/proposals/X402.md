# x402 payments for Convex

- Status: Draft
- Relates to: [CAD042](https://docs.convex.world/docs/cad/x402) (currently a stub), CAD010 (transactions), CAD019 (assets), CAD029 (fungible tokens), CAD041 (MCP)
- Upstream spec: [x402 v2](https://github.com/coinbase/x402/blob/main/specs/x402-specification-v2.md)
- Last updated: 2026-07-31

## Summary

Implement the [x402 protocol](https://www.x402.org/) — HTTP-native payments
built on the `402 Payment Required` status code — with Convex as a settlement
network. This enables payment-gated APIs and frictionless micropayments in CVM
coins and CAD29 fungible tokens, settled with sub-second finality and fees of
a few coppers.

The proposal has four parts:

1. A **protocol binding** defining how the x402 v2 `exact` scheme maps onto
   Convex: network and asset identifiers, a payment payload carrying a
   pre-signed Convex transaction, and verification/settlement rules. This part
   is destined to graduate into CAD042 and to be contributed upstream as
   `specs/schemes/exact/scheme_exact_convex.md`.
2. A new **`convex-x402` Maven module** holding the transport-agnostic
   protocol model, the `exact` scheme verifier, and facilitator core logic.
3. **`convex-restapi` integration**: facilitator endpoints
   (`/x402/verify`, `/x402/settle`, `/x402/supported`) and an `X402Gate`
   middleware that lets any peer operator payment-gate routes. This replaces
   the current hardcoded stub in `convex.restapi.api.X402`.
4. **Client support** so Java applications (and later the CLI/MCP) can detect
   a 402, construct and sign a payment, and retry.

A key structural advantage: a Convex peer can be **its own facilitator**.
Verification is a read-only query against local consensus state and settlement
is an ordinary transaction submission, so no third-party facilitator service
or custodial signer is required anywhere in the flow.

## Background: x402 v2 in brief

x402 v2 (`x402Version: 2`) is transport-layered. Over HTTP:

- A server requiring payment responds `402` with a `PAYMENT-REQUIRED` header:
  base64-encoded JSON of a `PaymentRequired` object — `x402Version`, a
  `resource` descriptor (`url`, `description`, `mimeType`), and an `accepts`
  array of `PaymentRequirements`:

  | Field | Meaning |
  |---|---|
  | `scheme` | Payment scheme identifier, e.g. `"exact"` |
  | `network` | Network identifier in CAIP-2 form (`namespace:reference`) |
  | `amount` | Required amount in atomic units, as a string |
  | `asset` | Asset identifier |
  | `payTo` | Recipient |
  | `maxTimeoutSeconds` | Maximum settlement time |
  | `extra` | Scheme-specific data (optional) |

- The client picks one requirement, constructs a scheme-specific payment, and
  retries with a `PAYMENT-SIGNATURE` header: base64 JSON of a `PaymentPayload`
  (`x402Version`, the `accepted` requirement, and a scheme-specific
  `payload`).
- The server verifies and settles (locally, or via a facilitator's
  `POST /verify` and `POST /settle` endpoints), serves the resource, and
  returns a `PAYMENT-RESPONSE` header with a `SettlementResponse`
  (`success`, `transaction`, `network`, `payer`, `amount`, `errorReason`).
- `GET /supported` on a facilitator lists supported `(scheme, network)` kinds.

The `exact` scheme transfers a precise, server-known amount. Each chain
binding must define its payload structure, verification rules and settlement
rules, and must guarantee: destination matches `payTo`, amount is exact, and
the facilitator can never be made a signer or source of funds.

On EVM chains the payload is an EIP-3009 `transferWithAuthorization`
signature; on Solana a partially-signed `TransferChecked` transaction. The
Convex binding below is the direct analogue using native signed transactions.

x402 also defines an MCP transport (payment data in
`_meta["x402/payment"]` / `_meta["x402/payment-response"]`), directly relevant
to the Convex MCP server (CAD041) — see Phase 3.

## Current state of the codebase

- `convex-restapi/src/main/java/convex/restapi/api/X402.java` is a skeletal
  placeholder: a `POST /verify` route that echoes back `payer` / `isValid` /
  `invalidReason` from the request without any on-chain verification, and an
  uncalled `respondPaymentRequired` with hardcoded v1-style fields. It is
  registered unconditionally in `RESTServer`. It establishes intent (including
  `asset: "slip44:864"` for the native coin) but implements nothing.
- CAD042 exists in the `design` repository as a stub noting the goal: x402
  for CVM coin and CAD29 fungible tokens.
- Everything an implementation needs already exists nearby:
  - `RESTServer` (Javalin 7 on Jetty, virtual threads) with `before`-handler
    seams used by admission control — the natural place for a payment gate.
  - `ChainAPI`'s prepare/submit flow and `PreparedTransaction` already handle
    externally-signed transactions, including storeless bounded decoding of
    client-supplied transaction blobs.
  - `convex.api.Convex` (local, remote binary, or HTTP via `convex-java`'s
    `ConvexHTTP`) for queries and transaction submission.
  - Transaction types `Transfer`, `Invoke`, `Call` in
    `convex.core.cvm.transactions`; Ed25519 signing via `AKeyPair` /
    `SignedData`.
  - `convex.fungible` / `convex.asset` CVM libraries for CAD29 tokens;
    CAD029 mandates CAIP-19 token IDs of the form `cad29:<address>`.
  - The `convex.auth` core (JWT, UCAN, DID) — not needed for the `exact`
    scheme, but the foundation for delegated/metered schemes later.

## Goals

- Full x402 v2 compliance for the HTTP transport and the `exact` scheme on
  Convex networks, interoperable with generic x402 client/server tooling.
- Non-custodial end to end: private keys never leave the payer; facilitators
  and resource servers only ever see signed transactions.
- Any Convex peer's REST server can act as facilitator and/or resource server
  with pure configuration.
- Support the native CVM coin first; CAD29 fungible tokens close behind.

### Non-goals (for this proposal)

- x402 v1 compatibility. There are no deployed Convex x402 clients, v2 is
  current, and Convex-scheme support requires new client code anyway.
- The `upto`/metered and batch-settlement schemes (future work; see Phase 3).
- Payment channels or off-chain netting. Convex settlement is fast and cheap
  enough that every payment can settle on-network.
- Fiat schemes, discovery ("Bazaar") listings, refund flows.

## Protocol binding (→ CAD042)

This section is the normative core and should move into CAD042 once agreed,
with a matching `scheme_exact_convex.md` contributed upstream.

### Network identifier

CAIP-2 form with a new `convex` namespace:

```
convex:<reference>
```

The `reference` MUST be the lowercase hex encoding of the network's genesis
hash, truncated to 32 characters (128 bits), mirroring the Solana convention
of truncating the genesis blockhash. This is unambiguous for private and test
networks without any registry. Well-known values (Protonet, the public
testnet) SHOULD be listed in CAD042 once computed from their genesis states.

A facilitator MUST reject payments whose `network` does not match the network
it settles against (`invalid_network`).

### Asset identifiers

| Asset | `asset` value | Atomic unit |
|---|---|---|
| Native CVM coin | `slip44:864` | copper (10⁻⁹ Convex Gold) |
| CAD29 fungible token | `cad29:<address>` per CAD029, e.g. `cad29:789` | the token's own integer units |

`amount` is always a base-10 string of atomic units. Requirements MAY include
`extra: {"decimals": <n>, "symbol": "<sym>"}` as a display hint (9 and `"CVM"`
for the native coin; the token's `decimals` callable otherwise). Scoped CAD29
assets (`cad29:<addr>-<scope>`) are deferred to a later phase.

`payTo` and `payer` are Convex account addresses in standard `#<n>` notation,
e.g. `"#13"`.

### `exact` scheme payload

The scheme-specific `payload` object is:

```json
{
  "transaction": "<hex of the CAD3 multi-cell encoding of a SignedData<ATransaction>>"
}
```

Hex is lowercase without prefix, consistent with the existing
`/api/v1/transaction/prepare` API. The signed transaction MUST take one of
two canonical forms:

- **Native coin** (`slip44:864`): a `Transfer` transaction
  `{origin, sequence, target, amount}` where `target` equals `payTo` and
  `amount` equals the required amount.
- **CAD29 token** (`cad29:<addr>`): a `Call` transaction with `target` equal
  to the token address, `offer` = 0, function `direct-transfer`, and args
  `[<payTo-address> <amount>]` — i.e. exactly
  `(call <token> (direct-transfer <payTo> <amount>))`.

No other transaction shape is acceptable: verification is structural, so the
facilitator never has to reason about arbitrary CVM code.

The payer is the transaction's `origin` account, which also pays juice fees.

### Verification rules

A facilitator (or self-verifying resource server) MUST check, against its
latest consensus state:

1. The payload decodes as a `SignedData<ATransaction>` within a strict size
   bound (4 KiB is generous; canonical payment transactions are under 300
   bytes). Decoding MUST be storeless and bounded, as `PreparedTransaction`
   already does for the prepare/submit flow.
2. The transaction matches one of the two canonical forms above for the
   `accepted` requirement's `asset`.
3. Destination equals `payTo` and amount equals `amount` exactly.
4. The Ed25519 signature verifies against the origin account's current
   account key. An account with no account key (actor) is invalid.
5. The transaction's sequence number equals the origin account's next
   sequence (current + 1). Lower means already spent (replay); higher cannot
   be confirmed.
6. Funds suffice: for the native coin, balance ≥ amount plus a fee allowance;
   for tokens, token balance ≥ amount (via `convex.fungible/balance`) and
   coin balance covers the fee allowance.
7. `x402Version` is 2, and scheme/network are supported.

`verify` is read-only and free. A successful `VerifyResponse` reports the
origin as `payer`.

### Settlement rules

1. Re-run verification (state may have moved since `verify`).
2. Submit the signed transaction unchanged via a Convex client and await the
   `Result`, bounded by `maxTimeoutSeconds` (and a facilitator-side cap).
3. Success iff the `Result` carries no error code. The `SettlementResponse`
   reports `transaction` as the hex SHA3-256 hash of the signed transaction
   (the `:tx` field of the Result info), plus `network`, `payer` and
   `amount`.
4. On a sequence error, the facilitator SHOULD check whether that exact
   transaction hash is already in consensus (it may itself have submitted it
   on a retried request) and, if so, report success idempotently.

Error mapping (Convex error code → x402 `errorReason`/`invalidReason`):

| Convex | x402 |
|---|---|
| `:FUNDS` | `insufficient_funds` |
| `:SEQUENCE` (unused, stale) | `invalid_exact_convex_payload_sequence` |
| bad signature | `invalid_exact_convex_payload_signature` |
| wrong shape/destination/amount | `invalid_exact_convex_payload_transaction` |
| timeout awaiting result | `invalid_transaction_state` |
| anything else | `unexpected_settle_error` |

### Properties and deviations

- **Replay protection** is inherited from CAD010 sequence numbers: a signed
  payment can settle at most once, network-wide, with no nonce bookkeeping in
  the facilitator. The same `PAYMENT-SIGNATURE` presented to two resource
  servers settles once; the loser sees a sequence error and refuses service.
- **Facilitator safety**: the facilitator never signs anything and holds no
  funds; it relays a transaction it cannot alter. Sponsorship abuse is
  impossible by construction.
- **Fees**: the payer's origin account pays juice fees in addition to the
  exact amount (a few coppers — of the order of 10⁻⁷ Convex Gold). This is a
  documented deviation from the strictest "only amount moves" reading of the
  exact scheme, comparable to other chains where someone must pay gas; here
  it is the payer rather than the facilitator, which is the safer default.
- **No validity window**: Convex transactions carry no `validBefore`. An
  unsettled signed payment remains valid until the payer's sequence advances;
  a payer can cancel outstanding payments by submitting any transaction (e.g.
  a zero-value self-transfer). Facilitators MUST settle promptly and MUST NOT
  hold signed payments. `maxTimeoutSeconds` bounds only the settlement wait.
- **Client sequencing**: because payments consume sequence numbers, a client
  making concurrent payments must serialise their construction. Client
  libraries SHOULD queue payment construction per account.

## Module design

### New module: `convex-x402`

A small, dependency-light module (depends on `convex-core` and `convex-peer`
only; JDK HTTP client, no new third-party dependencies). Rationale for a new
module rather than growing `convex-restapi` or `convex-core`: the protocol
model and scheme verifier are needed by servers *and* clients (and later the
CLI and MCP), must not drag Javalin in, and are integration-layer rather than
consensus code so do not belong in `convex-core`.

Packages:

- `convex.x402.model` — `PaymentRequired`, `ResourceInfo`,
  `PaymentRequirements`, `PaymentPayload`, `VerifyResponse`,
  `SettlementResponse`; JSON mapping (reusing the CVM-map-based JSON handling
  the REST API already uses, per CAD044) and base64 header codecs.
- `convex.x402.scheme` — `SchemeVerifier` SPI plus `ExactConvexScheme`
  implementing the verification rules above; network/asset identifier
  helpers (`ConvexNetworkId`, asset parsing for `slip44:864` / `cad29:`).
- `convex.x402.facilitator` — `Facilitator`: verify/settle/supported core
  logic written against `convex.api.Convex`, so it works identically with
  `ConvexLocal` (peer-embedded), `ConvexRemote` (binary) or `ConvexHTTP`.
- `convex.x402.client` — `X402Client`: wraps a `java.net.http.HttpClient`;
  on a 402, decodes `PAYMENT-REQUIRED`, selects a supported requirement,
  builds and signs the canonical transaction with an `AKeyPair` (querying
  the next sequence through a supplied `Convex` connection), retries with
  `PAYMENT-SIGNATURE`, and surfaces the decoded `PAYMENT-RESPONSE`.

Build wiring: parent `pom.xml` `<modules>` entry; `convex-integration`
dependency so it lands in `convex.jar`; module tables in `README.md` and
`AGENTS.md` (14 modules). `convex-p2p/pom.xml` is the minimal pom template.

### `convex-restapi` changes

Replace the `X402` stub with `convex.restapi.api.X402API`:

- **Facilitator endpoints** (config-gated, default on when x402 is enabled):
  - `POST /x402/verify` — body `{x402Version, paymentPayload,
    paymentRequirements}` → `VerifyResponse`.
  - `POST /x402/settle` — same body → `SettlementResponse`.
  - `GET /x402/supported` — `{kinds: [{x402Version: 2, scheme: "exact",
    network: "convex:<ref>"}...], extensions: [], signers: {}}` (`signers`
    is empty: the Convex scheme never requires facilitator signatures).
  - The facilitator base URL for clients is simply
    `https://<peer>/x402`. Endpoints carry `@OpenApi` annotations like the
    rest of `ChainAPI` so they appear in the generated OpenAPI docs.
  - Backed by a `Facilitator` over the server's existing `ConvexLocal` for
    verification queries, and peer submission for settlement. The existing
    bare `POST /verify` stub route is removed.
- **`X402Gate`** — a Javalin `before` handler (same seam as admission
  control) applied to operator-configured paths. Without a valid
  `PAYMENT-SIGNATURE` it responds 402 with the `PAYMENT-REQUIRED` header;
  with one it verifies and settles (settle-before-serve — mandatory for
  `exact`, since nothing stops a client replaying a verified-but-unsettled
  payment elsewhere), sets `PAYMENT-RESPONSE`, and lets the request through.
  Also exposed programmatically for embedders:
  `X402Gate.protect(routes, path, requirements, facilitator)`.
- **`RESTConfig`** gains a `rest.x402` section:

  ```json5
  rest: {
    x402: {
      enabled: true,
      facilitator: true,        // serve /x402/verify|settle|supported
      payTo: "#13",             // default recipient for gated routes
      routes: [
        { path: "/api/v1/premium/*",
          amount: "1000000",     // 1 silver = 0.001 gold
          asset: "slip44:864",
          description: "Premium data access" }
      ]
    }
  }
  ```

  Per-route `payTo`/`asset` overrides allowed. With `enabled: false`
  (default), no x402 routes or handlers are registered.
- Payment handling respects the existing hardening: request-size bounds,
  admission control, and a `ConcurrentLimit` on `/x402/settle`.

### `convex-java`

`ConvexHTTP`/`ConvexJSON` gain nothing mandatory — `X402Client` lives in
`convex-x402` and composes with them (using e.g. `querySequence`). If
`convex-x402` targets the parent's Java 21 bytecode, `convex-java` (Java 11)
must not depend on it; that is acceptable since the dependency runs the other
way. Should Java-11 clients need x402, `convex-x402` can set
`maven.compiler.release` 11 as `convex-java` already does — decide during
implementation.

### CLI / GUI

Not in scope for phase 1. Later: `convex x402 pay <url>` (picocli subcommand
in `Main.subcommands`) for scripting paid API calls, and GUI support in the
wallet/hacker tools.

## End-to-end flow

```
Client                        Resource server (peer REST)          Convex network
  | GET /api/v1/premium/data      |                                     |
  |------------------------------>|                                     |
  |   402 + PAYMENT-REQUIRED      |                                     |
  |<------------------------------|                                     |
  | build Transfer(origin,seq+1,  |                                     |
  |   #13, 1000000); sign Ed25519 |                                     |
  | GET ... + PAYMENT-SIGNATURE   |                                     |
  |------------------------------>| verify (local state query)          |
  |                               | settle: submit SignedData ---------->|
  |                               |         Result (no error) <----------|
  |   200 + body                  |                                     |
  |   + PAYMENT-RESPONSE          |                                     |
  |<------------------------------|                                     |
```

Typical added latency is one consensus round — well under a second on
Protonet — so settle-before-serve is affordable per request.

Java client sketch:

```java
AKeyPair kp = ...;                    // payer key
Convex convex = ConvexHTTP.connect(peerUri, address, kp);
X402Client client = X402Client.create(httpClient, convex, kp);
HttpResponse<String> resp = client.get(URI.create(paidUrl));
SettlementResponse receipt = client.lastPaymentResponse();
```

## Security considerations

- **Adversarial payloads**: headers and bodies are attacker-controlled, per
  the repo's public-API security stance. Bounded base64/JSON parsing, the
  4 KiB transaction cap, storeless CAD3 decoding, and structural whitelisting
  of transaction shapes keep the parse surface minimal.
- **DoS via free verification**: `verify` performs signature checks and state
  queries. It runs under the REST server's existing admission control plus a
  per-route concurrency cap, and does no writes.
- **Double-spend races**: two requests carrying payments with the same
  sequence both pass `verify`; consensus serialises settlement and exactly
  one succeeds. Settle-before-serve makes this safe for the server.
- **Front-running**: the submitting peer sees the payment before consensus.
  For a plain transfer to the operator's own account there is nothing to
  front-run, and the general mitigation is the established one — use trusted,
  well-staked peers — not protocol changes.
- **Facilitator trust**: a resource server using a *remote* facilitator
  trusts it to report settlement honestly (standard x402 posture). Running
  the facilitator in-process on the operator's own peer — the default here —
  removes that trust edge entirely.
- **No custody**: no component ever holds payer keys; the signing service and
  UCAN machinery are not involved in the `exact` scheme.

## Testing

- Unit tests in `convex-x402`: model round-trips (JSON/base64), and
  `ExactConvexScheme` against handcrafted good/bad transactions (wrong
  amount, wrong target, stale sequence, bad signature, oversized payload,
  non-canonical shapes, wrong network).
- Integration test in `convex-restapi`: launch a local peer plus `RESTServer`
  on port 0, gate a test route via config, pay for it with `X402Client`, and
  assert the transfer in final state and the `PAYMENT-RESPONSE` receipt.
  Waits on futures/results only — no sleeps, no fixed ports.
- Interop check: validate `PaymentRequired`/`PaymentPayload` JSON against the
  upstream x402 schemas (the upstream repo publishes reference types) so
  generic x402 tooling can parse Convex requirements.

## Phasing

1. **Phase 1 — core + native coin**: `convex-x402` module (model, exact
   scheme for `slip44:864`, facilitator core, client), REST facilitator
   endpoints + `X402Gate` + config, stub removal, tests, CAD042 rewrite from
   this document.
2. **Phase 2 — CAD29 tokens and polish**: `cad29:<addr>` assets via the
   canonical `direct-transfer` call form, `extra` decimals/symbol hints,
   CLI `convex x402 pay`, idempotent-settle refinement, upstream
   `scheme_exact_convex.md` PR and CAIP-2 `convex` namespace registration.
3. **Phase 3 — beyond exact**: MCP transport for paid tools on the CAD041
   server (`_meta["x402/payment"]`), scoped CAD29 assets, and a metered
   `upto`-style scheme — a natural fit for the UCAN delegation machinery in
   `convex.auth` (a payer-signed UCAN authorising spend up to a cap, settled
   in aggregate).

## Open questions

1. Genesis-hash CAIP-2 references need the well-known values computed and
   published (Protonet, testnet) — and confirmation that truncated genesis
   hash is preferred over human-readable aliases.
2. Should `convex-x402` target Java 11 bytecode (like `convex-java`) so
   lightweight clients can use it, or the parent's Java 21?
3. Is `slip44:864` confirmed as the registered SLIP-44 coin type to
   standardise on for the native coin (the existing stub suggests yes)?
4. Facilitator write-access policy: should `/x402/settle` be available on
   fully public peers by default, or gated behind `rest.x402.facilitator`
   with operators opting in (proposed: opt-in via config, on by default only
   when x402 itself is enabled)?
5. Fee allowance constant for verification (rule 6): fixed headroom in
   coppers vs computed from current juice price.
